# Local upload failure and code sweep — 1 October 2026

The local upload failure came from a server process still running an older implementation against the migrated SQLite workspace. Its run insert supplied seven positional values to a table that now has ten columns. The incompatibility reproduces as `table runs has 10 columns but 7 values were supplied`.

The server was restarted with the current implementation, which names the insert columns. A regression test uploads successfully even after another database column is added. The UI now checks the API contract and a server source fingerprint; an incompatible or stale server gives restart instructions. Unexpected request failures return a reference that can be matched to the server traceback.

A SQLite backup was taken before restarting the server, under `kaizen-workspace/backups/`. Existing source changes and saved reviews were preserved.

## Fixes

| Area | Failure addressed | Result |
| --- | --- | --- |
| Uploads | Duplicate, traversing and conflicting paths; unsupported extras; oversized files; unusable CSV/PDF content | Clear client errors, bounded streaming, and cleanup after failure. Folder and individual-file uploads are supported. |
| Run registration and copying | A later database error could leave a partially registered run or copied review | Nested transactions defer store commits and roll back the complete operation. Failed run directories are removed. Saved JSON uses atomic replacement. |
| API validation | Malformed mutation bodies, pagination, rendering DPI and nonfinite business parameters could reach implementation errors | Typed request bodies and bounded query parameters produce validation errors. Search covers both source descriptions and item numbers. |
| Terminology | Concurrent updates could overwrite history; reusing an existing/deleted ID could replace it; run linkage could record a newer relationship than the engine used | Updates and history writes are atomic. IDs with history cannot be recreated. Run linkage and retrieval use the run's terminology snapshot. Audit authors come from the authenticated session. |
| Review and Excel import | Bulk acceptance could overwrite a concurrent edit; imports could partially apply; same-second edits could escape conflict detection; dry runs wrote audit events | Whole-operation transactions, microsecond timestamps, no database writes during dry runs, workbook cleanup, and bounded import sizes. |
| Action items | Concurrent creation could allocate the same ID; absent or uncertain comparisons could be treated as fixes; corrective runs could not verify earlier items | Atomic ID allocation. Verification requires an actual comparison that needs no validation. Compare-runs verification accepts an explicitly selected earlier run and requires edit access to both. Reopening clears resolution metadata. |
| Copies | Resolved action items retained their status after their resolution links were reset | Those items reopen in the independent copy. Approvals continue to require approval in that copy. |
| PCO checks | Ambiguous substitute rows and incomplete extraction could auto-clear; invalid numeric proposals could be silently ignored | These cases require review. Numeric parsing rejects NaN and infinity. |
| Label revisions | Already-present changes ignored the proposed quantity; consumed expectations changed repeated results; unrelated substitutions produced false removals; unreadable revisions could appear checked | Quantity checks cover already-applied substitutions/additions. Expectations are copied per comparison. Approved substitutions explain outgoing removal. Incomplete extraction and missing REF identity block validation. |
| Coverage and run diff | An old label counted as current coverage; uncertain later results appeared resolved | Old-only sets report missing current labels. A later comparison still needing validation remains open. |
| UI | Switching runs/rows briefly exposed previous data; view-only users saw unavailable mutations; invalid offsets and uploads were confusing | Async data is tied to loader keys, permission-dependent controls are disabled/hidden, offsets are sanitized, and upload errors are explained. Empty or incomplete runs cannot show a cleared overview. |
| Business report | Runs with no item comparisons could claim 100% savings | No completed comparisons means zero established savings and an unmet target. |
| Cleanup | Unused imports, redundant identity fallbacks, obsolete router options and script statements | Removed the unused code and kept CLI workflows that still use the legacy review store. |

## Review approval and overview follow-up

The overview used original engine validation counts while the runs list used a summary saved at
registration. The default queue also filtered the original engine flags. Consequently, approving
a row did not reduce the prominent pending count, and a saved override could be displayed while
classification filters still matched its original recommendation.

The API now builds one current review snapshot for progress, states and queue filtering. The
overview shows pending reviews, approvals and unresolved findings separately. The runs list uses
the same live progress. An approved Exact/Equivalent assessment clears the current finding;
confirming a discrepancy completes review but keeps the finding visible. Needs-more-information
decisions remain pending, and editing an approved row reopens review. Original engine evidence
and counts are retained and explicitly labeled.

The overview's extra queue request and 5,000-row aggregation ceiling were removed. Classification
filters and queue priorities use the current assessment; links to original automated results use
an explicit engine filter. New reviewer findings on originally clean rows are counted and can be
filtered. Read-only views refresh after successful mutations, across browser tabs, on focus and
periodically while visible. Late action-verification responses cannot appear under a different run.
Missing saved runs no longer make the entire runs list fail.
The business-case and terminology pages now label their original engine counts and future-run
estimates, so those figures cannot be mistaken for the remaining approval queue.

The local server was rebuilt and restarted with API contract 3. An actual HTTP test in an isolated
workspace uploaded two PDFs, saved and approved a review override, and checked the overview,
runs list and queue: pending reviews changed from 1 to 0 and approved rows changed from 0 to 1.
Excel, PDF and ZIP exports and copying continued to return 200; an invalid PDF returned 400.
No test account or test run was added to the user's workspace.

## Limits and operating notes

The golden accuracy result applies to the checked-in dataset. OCR and new document layouts still need the existing source-evidence review described in `known-limitations.md`. A code sweep and regression suite do not prove that every possible input is bug-free.

Browser control was unavailable, so no visual browser walkthrough was performed. UI behavior was checked with rendered React component tests, hook tests, API tests and the production build. The build retains a nonfatal bundle-size warning; Python tests retain two third-party deprecation warnings.

There was no active approved account session available for an authenticated upload into the user's workspace. The HTTP upload smoke test therefore used a separate temporary account/workspace and did not create test runs in the user's saved data. Refresh the local app, sign in if prompted, and retry the original upload.

Historical ownerless runs created by the old server were preserved. Ownership recovery needs an explicit choice of owner; this sweep does not guess ownership or remove saved runs.

The dependency fixes follow the maintainers' [Vite advisory](https://github.com/vitejs/vite/security/advisories/GHSA-fx2h-pf6j-xcff) and [Vitest advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9), with the complete dependency graph checked by npm audit.
